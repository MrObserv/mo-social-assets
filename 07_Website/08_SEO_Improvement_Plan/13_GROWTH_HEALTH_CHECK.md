## Cadence

## Start-of-session block (do this before anything else)

1. **Read the system clock and stamp the ACTUAL run date.** Never infer the date from the Monday/Thursday cadence, from the previous report's filename, or from any hardcoded value. The date that goes in the report heading, the three report filenames, the tracker row and every Ops_Log row is the one the clock returns, full stop.
2. **State the weekday, and say so when the run is off-cadence.** If the clock says the day is not a Monday or a Thursday, the report must carry an explicit line saying the run fired off-cadence and on what day. An off-cadence run is allowed; a silent one is not.
3. **Check for a same-day collision before writing.** If a report already exists for today's date, refresh it in place. If a report exists for a DIFFERENT date, leave it alone. Never restamp, rename or overwrite another run's file (see the incident note below).
4. **Read `00_Command_Center/System_Changelog.md`** for entries post-dating the previous run, and act on them before acting on anything else.

> **INCIDENT NOTE, 2026-08-23 (why rule 1 and rule 3 exist).** An off-cadence Sunday session inferred its date from the cadence, concluded it was 2026-08-17, and wrote over the genuine 2026-08-17 Monday reports. It then "corrected" those files to say 2026-08-23 and raised a CR asking for them to be renamed. Both moves were wrong. Control reversed the restamping on 2026-08-24 (GR-2026-08-23-04) after four independent checks put the reports firmly on 17 Aug: the Drive creation timestamp, the newest post the body knew about, the 558 subscriber figure that the 24 Aug run carries as its prior, and a GSC window ending 15 Aug, which is a two-day lag off a 17 Aug read and an implausible eight-day lag off a 23 Aug one. **Reading the clock is the cheap fix. Overwriting a sibling run's file is the expensive failure.**

## The seven sections (each run)

1. **Subscribers & growth.** Active total, new / churned / net; **click-through rate + click-to-open rate as the HEADLINE newsletter engagement metric** (opens are secondary and inflated by Apple Mail Privacy Protection, 2026 refresh); earnings; top acquisition sources.
   - **Standing segment snapshot table (added 2026-08-24, GR-2026-08-23-04).** Every segment the publication holds, in one table, every run: segment name, `num_members`, the move since the last run, open rate, CTR, CTR move. Pull it with `list_segments` (one call returns members and metrics for all of them). Sizes were never tracked run to run before this, which is why Warm Contributors sat at 59 for three weeks and a nudge pool that has never once shrunk only surfaced when Al asked directly. **Flag any segment that is flat or moving the wrong way across three or more runs**, and say plainly what the segment was built to do that it is not doing. Baseline for week-over-week movement is the eight-segment table in `_Health_Checks/2026-08-23_ADDENDUM_segments_and_polls.md`.
   - **Same-day caveat.** If the previous snapshot was taken less than a full cadence period ago, say so and do not read flatness as a stall.

2. **Website & SEO traffic.** Unique visitors / sessions / bounce / session-duration trend; top pages; top referrers; GSC keyword movement vs plan targets. State the GSC window's end date explicitly, because it lags the run date by two to three days and that lag is one of the checks on whether the run date is right.

3. **Lead magnets & funnel.** Traffic to `/free-chapter`, `/advisory`, `/products/...chapter-4`, `/book` vs their capture + nurture; **flag any lead-magnet automation still in DRAFT** (a live page with no live follow-up is a leak).

4. **Automations health.** Live vs draft; enrolled / completed; open + click; flag unpublished or broken flows and stale test automations.
   - **Reconcile poll votes against router enrolments (added 2026-08-24, GR-2026-08-23-04).** For every poll that drives a router automation, put the per-choice vote count next to the matching automation's enrolment count and show the two side by side. They should match. Any gap is a routing failure and gets a named flag, not a footnote. **Do this while the numbers are small enough to audit by hand.**
   - **Live case to close:** the stream poll `poll_9f31d69f` records **2 Leadership votes** (11 Aug and 20 Aug) against **1 enrolment** on `aut_48c6e2da`, while Technical reconciles 4/4 and Both 5/5. One Leadership vote did not enrol. This **corrects** GR-2026-08-23-03's finding that the three stream routers are "live and correct": two of the three are. Audit the missing one by hand and record the outcome here.

5. **Surveys & feedback.** New responses since last run; audience makeup (occupation and the clean Role field); topic interest; self-reported acquisition channel; and the **contributor/collaboration pool** (subscribers who said Yes/Maybe to contributing and have had no follow-up).
   - **Report response rate PER APPEARANCE, never as a share of total subscribers (added 2026-08-24, GR-2026-08-23-04).** For every poll and survey, state the **appearance count** first, then completions, then completions per appearance. A poll that has been shown once has been offered to one send's worth of readers, not to the whole list. The old whole-list denominator produced a false "1.8% response, subscriber input is not working" reading on a stream poll that had exactly ONE appearance and took 11 votes, 8 of them inside 24 hours. That is a healthy response to a single exposure. **If the appearance count is low, the finding is an exposure problem, not an audience problem, and the report must say which.**
   - **Re-surfacing check.** Any poll or survey named "standing" must have a defined re-appearance rule and an appearance count above 1. Flag any that does not: `poll_d99ab91d` was created 21 Aug as "standing" and still shows 1 appearance and 0 completions, so "standing" is not yet true of it.
   - **Subscriber-visible string check (§5 voice, added 2026-08-24).** Poll names, survey names, segment names shown to readers, choice labels and automation email subjects are all reader-facing strings and the **§5 em-dash ban is global and register-independent**, so it binds them. Scan them every run and flag any breach. **Open breach:** `poll_d99ab91d` is named "The Signal (em dash) Issue Rating (standing)", carrying a literal em dash where the words are. Correct name: **`The Signal: Issue Rating (standing)`**. The poll is published and therefore locked, so the connector cannot rename it; this is a UI move for Al.
   - **Poll re-ask quality rule (added 2026-08-24, from the only written reply the stream poll received: "I would have appreciated in this email an example of articles for each option").** A choice between two bare labels is not a fair question. Every stream-poll appearance must **name one example piece under each option**. Standing examples, all live:
     - *Technical deep-dives*: "What Are Wide Events? Observability 2.0, Without the Hype" (`/p/what-is-a-wide-event`)

   - **Read the split as directional only.** The 11-vote result (Both 5, Technical 4, Leadership 2) does **not** support a hard two-stream split: 45% explicitly asked for both. Do not let a two-figure sample drive a programme decision.
   - **Warm-contributor tracker check (GR-2026-07-08-04).** Read `15_WARM_CONTRIBUTOR_TRACKER.md` every run and raise a flag for any row whose Status is **REPLIED / HOT** but whose "Owed / next action" is still open (a promised piece not sent, a reply not answered). 6. **Rising themes.** Rising observability terms feeding the SEO plan + Tech Tuesday / byte-size ideation.
   - **Google Trends is BACK IN, read by screenshot (Al-directed 2026-08-24, reversing the same-day GR-2026-08-23-04 retirement).** The earlier retirement said Trends "never returns data": that was true only of the TEXT extraction. `get_page_text` cannot see the canvas chart or the Rising panels, but a **screenshot can**, and a manual test on 2026-08-24 read the interest chart, the region breakdown and the Rising related-queries panels cleanly. Control to register this reversal in `System_Changelog.md`.
   - **Method (screenshot, not text):** via Claude in Chrome, open a tab, navigate to a single-term explore URL `https://trends.google.com/trends/explore?date=today%203-m&q=<TERM>&hl=en`, wait ~5s, then scroll to the bottom and screenshot the **Related queries (Rising)** and **Related topics (Rising)** panels. **Retry-on-timeout is mandatory:** the renderer intermittently times out on the first `screenshot` call and succeeds on an immediate second call, so always retry once before concluding a failure. Read the panel values off the screenshot.
   - **Seed with NARROW domain terms, one at a time, not the broad set.** The bare seed "observability" returns junk (calendar artifacts, non-English noise, and the control-theory meaning: on 2026-08-24 its rising queries were "hospitales" and "observability matrix"). Domain terms return usable signal: "OpenTelemetry" returned "otel collector" and "litellm". Use the rotation **OpenTelemetry, AIOps, observability cost, AI SRE** (swap in a current term when one goes stale). The multi-term comparison view has NO related-queries panel, so single-term explores are required for Rising terms.
   - **WebSearch stays the co-primary**, supported by the Gmail curation feeds and the on-demand Reddit pull; Trends is the corroborating read, not the sole source, because even readable Trends is thin for niche B2B terms. Only report "Google Trends unavailable" if the screenshot method genuinely fails after a retry, and say which term and step failed.
